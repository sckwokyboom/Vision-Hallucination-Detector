# Unified comparison — every system on one eval set, one scorer

Generated by `scripts/unified_table.py`. Regenerate with the exact command in
[Reproduce](#reproduce) at the bottom.

**Eval set:** the 202 English items of the frozen, image-grouped `tune_dev` split
(`splits/en.eval_protocol.json`, applied to `splits/dev.en.jsonl` via `--eval_ids`). This is the
set every trained connector run was evaluated on, so the SHROOM starter baseline was re-run on
exactly the same items.

**Scorer:** all rows are re-scored here from their submission JSONL by the same code, over the
**full gold response length**. Two of the numbers deserve reading carefully:

| column | meaning |
|---|---|
| `span_iou` | char-IoU of the spans the system would actually submit (`pred_labels`). The official metric. |
| `Δ vs floor` | mean per-item IoU minus predict-nothing, with a 2000-sample **paired bootstrap** 95% CI. Bold `span_iou` = CI excludes 0 on the up side. |
| `span_iou@thr` | char-IoU at the best single threshold swept over `char_probs`. Decoder-independent — compares the underlying per-character signal, not the decode rule. |
| `roc_auc` / `pr_auc` | threshold-free, from `char_probs`. Trivial systems sit at 0.500 / 0.168 (the positive rate). |
| `cor` / `cor_sub` | Pearson(gold per-char prob, predicted per-char prob). `cor_sub` zeroes the probabilities on items the system decoded to `[]` — what a gated system actually submits. |

## 2. What the table says

1. **The SHROOM starter baseline is below the predict-nothing floor and carries no signal.**
   0.1999 / 0.2005 span_iou vs a 0.2129 floor, roc_auc 0.495, calibration −0.03, per-category
   macro 0.499. It abstains on 93–94% of items and, on the few it does fire, it is wrong often
   enough to lose more than it gains. Giving it our forgiving aligner makes it *worse* (0.1797),
   which confirms the problem is the detector, not span alignment.
2. **Every trained readout beats the floor with a CI that excludes zero.** Best is the BIO-head
   variant at **0.3202 (+0.107 over the floor)**, then linear+gate_hyst s13 at 0.3041 (+0.091).
   Against the starter baseline that is roughly **+0.12 span_iou**, and 0.495 → 0.672 roc_auc.
3. **Decoder choice moves span_iou more than it moves the signal.** `span_iou@thr` — the same
   probabilities scored without any decoder — sits in a narrow 0.259–0.286 band for every trained
   row, while decoded `span_iou` ranges 0.272–0.320. The BIO head has the *best* decoded IoU and
   the *worst* `span_iou@thr`; it wins by decoding, not by a better per-character signal.
4. **The seed spread is ~0.02 span_iou** (s13 0.3041 vs s42 0.2850, same config). Any two configs
   within ~0.02 of each other are not distinguishable on this set.
5. **4-bit vs 8-bit features is a null** (0.2902 vs 0.2810 on a 1k-train budget — within the seed
   spread). Keep 4-bit.
6. **Calibration is where the trained systems really separate from prompting**: cor 0.27–0.37 vs
   ≈0 (or negative) for every zero-shot system ever measured.

## 3. Caveats you must not drop when reporting these numbers

- **`tune_dev` is a tuning set, not a test set.** For every connector row, `tau`/`g_thr` were
  selected by sweeping on these same 202 items, so the decoded `span_iou` is optimistic. The
  held-out 157 items (`splits/en.eval_protocol.json → heldout`) have **never been scored**. Before
  submitting, re-score the chosen system there with a `tau` frozen from `tune_dev`.
- **The starter baseline is not tuned at all**, so the comparison is generous to *our* systems.
  It is still the right comparison to publish — that is the baseline as the organizers ship it —
  but the fair way to state it is "our decoder is tuned, the starter has nothing to tune".
- **The starter ran on MLX 4-bit Qwen2-VL-2B**, not bf16 on the cluster, and with images capped at
  512 px (matching the starter's `max_pixels=512*512`). Greedy and T=0.5 land within 0.0006 of each
  other, and the number reproduces the earlier 200-item measurement (0.199), so quantization is not
  what is holding it down.
- **Numbers here are 0.001–0.003 lower than the `summary_*.json` files** in the same directories.
  That is not noise: the training pipeline truncates answers to 1200 characters and scored IoU over
  the truncated length, while this table scores over the full gold response. 19 of 202 items are
  longer than 1200 chars (worst: `train-en-1289`, 2859 chars). Those tail characters can never be
  flagged by the current model — a real, if small, submission bug.
- **Only English.** fr / it / zh are ranked separately by the organizers and nothing here has been
  run on them.

## Reproduce

Baseline (≈3 min on an M-series Mac, 0.8 s/item):

```bash
.venv/bin/python scripts/mlx_predict.py --model_id mlx-community/Qwen2-VL-2B-Instruct-4bit --input splits/dev.en.jsonl --eval_ids splits/en.eval_protocol.json --image_dir ../Shroom-Vision/images --output results/baseline/starter_qwen2vl2b_t05.jsonl --prompt_style original --temperature 0.5 --max_tokens 1024 --max_side 512 --save_raw
```

Starter-faithful alignment, then the table:

```bash
.venv/bin/python scripts/starter_strict.py --pred results/baseline/starter_qwen2vl2b_t05.jsonl --output results/baseline/starter_qwen2vl2b_t05_strict.jsonl
```

```bash
.venv/bin/python scripts/unified_table.py --gold splits/dev.en.jsonl --eval_ids splits/en.eval_protocol.json --pred "starter=results/baseline/starter_qwen2vl2b_t05_strict.jsonl" --pred "bio=results/v3_mac/dev_pred_linear_bio_tv_bio_gc_ctr_notype_s13.jsonl" --pred "gate_hyst=results/fullscale/dev_pred_linear_gate_hyst_s13.jsonl" --out docs/comparison.md
```

`--eval_ids` filters the dev split down to the frozen `tune_dev` 202 in-memory, so no
materialised gold subset has to exist (or be committed) for this to reproduce.

Machine-readable copy of every metric: `results/comparison.json`.
